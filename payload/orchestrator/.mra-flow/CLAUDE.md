## Orchestrator layout

This repo is an **orchestrator**. It holds no application code.

| Path | Holds | Git |
|---|---|---|
| `openspec/` | specs, changes, the `mra-flow` schema | this repo |
| `docs/adr/`, `GLOSSARY.md` (multi-context: `docs/GLOSSARY-MAP.md`, `docs/<key>/`) | architecture decisions and domain language: shared by all code repos, or one context per code repo (see Domain docs) | this repo |
| `docs/roadmap/` | initiative roadmaps from `/mra-roadmap`: slices (one future change each), estimates, totals, actuals in effective hours; `<initiative>-effort.md`, generated by `.mra-flow/bin/mra-effort report`: estimate vs. actual per slice and hours per phase; rules in `.mra-flow/docs/agents/roadmap.md` | this repo |
| `docs/research/` | cited research notes from `/mra-research`, the evidence ADRs and designs point at | this repo |
| `docs/prototypes/` | prototype notes and screenshots from `/mra-prototype`: the accepted verdicts `design.md` and `/mra-qa-ui` point at | this repo |
| `.beads/` | the beads issue database for all code repos | this repo |
| `.claude/skills/mra-*`, `.mra-flow/` | the workflow skills, hook, docs and `mra-repo`, installed by mra-flow | this repo |
| `mra-flow.toml` | the repo registry: one `[repos.<key>]` table per code repo, with `path`, `remote`, `description`, `depends_on`, optional `ui_paths` (paths whose changes `/mra-qa-ui` checks in a browser), optional `drift = false` (out of scope: the drift check hook and `/mra-drift` ignore it); optional `[integration] command` (how `/mra-archive` and `/mra-hotfix` integrate a repo's branch, instead of `finishing-a-development-branch`) | this repo |
| each repo's `path` | a code repo | separate repo, git-ignored here |
| `.worktrees/<change-id>/<key>` | per-change worktrees of the code repos, branch `change/<change-id>` | git-ignored here |
| `.worktrees/proto-<slug>/<key>` | throwaway prototype worktrees, branch `prototype/<slug>`, removed after the verdict | git-ignored here |

Build, test and stack conventions live in each code repo's own `CLAUDE.md`. `.mra-flow/bin/mra-repo list` prints the code repos in integration order (dependencies first); `mra-repo add` declares a new one (`--ui-path` for its UI paths), `mra-repo ui-paths <key>` prints a repo's UI paths and `mra-repo clone` restores missing clones. Until at least one is declared, a SessionStart hook recommends `mra-repo add` every session, and `/mra-grill`/`/mra-propose` recommend it too before proceeding. `.mra-flow/bin/mra-effort` measures a change's effective hours per phase from the Claude Code session logs (`measure`), writes them into a roadmap (`record`) and regenerates its totals and estimate-vs-actual report (`report`).

## Workflow

Every feature goes through the `mra-flow` workflow (diagram: `.mra-flow/docs/mra-flow.md`; keep it in sync when an `mra-*` skill changes). Start each phase with its command:

| Phase | Command | Output |
|---|---|---|
| (optional) explore | `/mra-explore [idea]` | understanding only, nothing written |
| (optional) roadmap | `/mra-roadmap <topic> \| <initiative> \| --from <map> \| --retro <initiative>` | `docs/roadmap/<initiative>.md`: estimated slices and totals; ADRs, glossary; initiative epic + one epic per slice |
| 1. grill | `/mra-grill <topic>` | `GLOSSARY.md` terms, ADRs in `docs/adr/` |
| 2. propose | `/mra-propose <change-id>` | OpenSpec change: proposal, specs, design, tasks |
| 3. track | `/mra-track <change-id>` | beads epic + one issue per task |
| 4. build | `/mra-build <change-id>` | code in the worktrees, one commit per issue |
| 5. verify | `/mra-verify <change-id>` | pass/fail report, findings filed as beads bugs |
| 5. verify (UI) | `/mra-qa-ui <change-id>` | run by verify when `ui_paths` are touched, or alone: browser checks, findings filed as beads bugs (`qa-ui`) |
| 6. fix | `/mra-fix <change-id> [bug]` | bugs fixed test-first; then back to verify |
| 7. archive | `/mra-archive <change-id>` | branches integrated, change archived, epic closed |
| any time | `/mra-update <change-id>` | revised artifacts, beads reconciled |
| rare | `/mra-sync <change-id>` | delta specs merged into main specs before archive |
| rare | `/mra-hotfix <bd-id \| bug>` | bug in an archived feature fixed test-first, verified and integrated |
| any time | `/mra-drift [capability]` | drift report: specs vs. real code, read-only |
| when stuck on a fact | `/mra-research <question> [--change <id>]` | cited note in `docs/research/` |
| when stuck on design, or a new UI screen | `/mra-prototype <question>` | note in `docs/prototypes/`, verdict as ADR or carried decision; prototype kept on branch `prototype/<slug>` |
| end of session | `/mattpocock-skills:handoff [next focus]` | `handoff/ho-<datetime>.md` (`read: false`), auto-loaded once by the next session (handoff rules: installed with `install.sh --user`) |

Rules:

- Never implement through `/opsx:apply` or the `openspec-apply-change` skill: implementation is `/mra-build`.
- An `mra-*` command whose argument is a question instead of what its argument hint asks for gets an answer in the context of the current phase; the phase is not restarted.
- Write code only in `.worktrees/<change-id>/<key>` (or `.worktrees/hotfix-<bd-id>/<key>` for `/mra-hotfix`, `.worktrees/proto-<slug>/<key>` for `/mra-prototype`), never in this repo and never on the code repos' main branch.
- Every UI change is seen before it is specified: a prototype for a new screen, navigation element or interaction pattern, a sketch for a change to an existing screen. `/mra-grill` offers it, `/mra-propose` and `/mra-update` check it; see `.mra-flow/docs/agents/ui-preview.md`.
- An effort too large for one change gets a roadmap first: `/mra-roadmap` (or `/mattpocock-skills:wayfinder`, then `/mra-roadmap --from <map>`, when it is mostly open decisions). Then each slice goes through `/mra-grill` → `/mra-archive` like any change; the phase skills keep its row up to date. Without a roadmap nothing changes. See `.mra-flow/docs/agents/roadmap.md`.
- The other `/opsx:*` and `/mattpocock-skills:*` commands stay available for one-off use; the `mra-*` commands are the default path.

### Spec drift

`openspec/specs/` is written once per change; colleagues' other work on the code repos never touches it, so it can go stale.

- Before `/mra-grill` or `/mra-propose` on a capability that already has a spec, run `/mra-drift <capability>` and resolve DRIFT-SPEC items first (both skills ask this on your behalf; you can also run it yourself first).
- After `/mra-hotfix`, or any manual change that alters specified behaviour, run `/mra-drift <capability>` and sync the spec.
- A SessionStart hook (`.mra-flow/hooks/check-drift.py`) checks the code repos' default branches on every new session and recommends `/mra-drift` when one moved since the last check; it only recommends, never runs it. Its state file, `.mra-flow/drift-state.json`, is local and git-ignored.
- A second SessionStart hook (`.mra-flow/hooks/check-update.py`) asks the mra-flow remote at most once every 24 hours for its newest release tag and, while it is newer than `.mra-flow/version`, tells the session to recommend the update command (never to run it). Its state file, `.mra-flow/update-state.json`, is local and git-ignored; `MRA_FLOW_REMOTE` overrides the remote.

### How this overrides the beads defaults

The beads context injected by `bd prime` is subordinate to this section (task tracking and memory rules come from the user-level conventions):

- **When issues are created:** only in `/mra-roadmap` (initiative and slice epics, never tasks), `/mra-track`, `/mra-build`, `/mra-verify` (and its `/mra-qa-ui` step), `/mra-fix`, `/mra-hotfix` and `/mra-update`. Exploring, grilling and proposing create no issues.
- **Creating issues:** sequentially, from the skill doing the work; no parallel subagents for issue creation.
- **Commit authority:** invoking `/mra-build` or `/mra-fix` authorizes commits on the `change/<change-id>` branches inside `.worktrees/`. Invoking `/mra-hotfix` authorizes commits on its `hotfix/<bd-id>` branches. Invoking `/mra-prototype` authorizes commits on its `prototype/<slug>` branch, which is never merged or pushed. Push, merge and PRs happen only in `/mra-archive` and at the end of `/mra-hotfix`, with the user choosing the option per repo (or, when `mra-flow.toml` declares an `[integration] command`, choosing between that command and keep). Commits in this orchestrator repo always need the user's confirmation.

## Agent skills

### Issue tracker

Issues live in beads (`bd`), in this orchestrator repo's database, and cover all code repos. See `.mra-flow/docs/agents/issue-tracker.md`.

### Triage labels

The five default canonical labels (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`), applied as beads labels. See `.mra-flow/docs/agents/triage-labels.md`.

### Domain docs

Single-context by default: one `GLOSSARY.md` + `docs/adr/` at the orchestrator root, shared by all code repos. Multi-context when `docs/GLOSSARY-MAP.md` exists: one `GLOSSARY.md` + `adr/` per code repo under `docs/<repo-key>/`, plus the root `docs/adr/` (and, lazily, `docs/GLOSSARY.md`) for decisions/terms spanning repos. See `.mra-flow/docs/agents/domain.md`.
